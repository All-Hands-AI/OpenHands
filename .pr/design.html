Quiet backend logs by default

Launching Canvas printed several hundred lines of library-internal startup chatter, burying the handful of lines a user needs. This PR makes a default launch readable and keeps the noise available behind an explicit opt-in.

PR #18830 · Fixes #18823 · 7 files · +624 / −13 · head 02d279d6c · base c69d5291b

01What changed

Both backends that Canvas spawns read LOG_LEVEL and default it to INFO. At INFO the automation service's logging setup raises every registered logger — including sqlalchemy.orm — so the SQLAlchemy model mapper narrates its own construction and prints 338 lines before the service is even reachable. The launcher never set a level, so that was the default experience.

This PR defaults both backends to WARNING in the shared launcher helper and in the Docker entrypoint. An explicit LOG_LEVEL / AUTOMATION_LOG_LEVEL still wins, and --verbose opts back into DEBUG. Uvicorn's own --log-level is set from the same resolved value, because that flag — not LOG_LEVEL — governs the startup banner and the per-request access lines.

★ The choice of WARNING over ERROR is load-bearing.

ERROR would have silenced the flood too, but it also hides a real, actionable warning this repo emits today: Workspace retention is enabled but the configured root … does not exist on this host; no workspace will be purged. WARNING is the smallest change that removes the noise while keeping signals a user can act on.

The launcher gains one shared helper

scripts/dev-safe.mjs now owns the policy, so every launch path resolves the level the same way instead of each re-deriving it: 

export const DEFAULT_BACKEND_LOG_LEVEL = "WARNING";   // dev-safe.mjs:819

export function backendLogLevel({ verbose = false, env = process.env } = {}) {
  return verbose ? "DEBUG" : env.LOG_LEVEL || DEFAULT_BACKEND_LOG_LEVEL;   // :834
}

export function buildBackendLogEnv({ verbose, automation, env } = {}) {
  const level = backendLogLevel({ verbose, env });
  return {
    LOG_LEVEL: level,
    ...(automation ? { AUTOMATION_LOG_LEVEL: verbose ? "DEBUG" : env.AUTOMATION_LOG_LEVEL || level } : {}),
  };
}

Precedence is deliberate and matches how the services themselves resolve their settings: an explicit environment variable is the strongest signal, --verbose overrides even that because it is a per-invocation instruction, and the quiet default applies only when neither is present.

Why Uvicorn's flag is set separately

Uvicorn takes a lowercase level name and applies it to its own loggers, which are distinct from the application's. Setting only LOG_LEVEL would leave the startup banner and one access line per request at INFO. Measured on a real launch, access lines go from 1 to 0. --verbose restores them.

Docker follows the same default

docker/entrypoint.sh defaults both variables and passes the resolved level to both Uvicorn invocations. The two lines are marked with a delimited block (# >>> backend-log-level … # <<< backend-log-level) so the new test can extract and execute exactly those lines rather than grepping the whole script: 

# docker/entrypoint.sh:308
export LOG_LEVEL="${LOG_LEVEL:-WARNING}"
export AUTOMATION_LOG_LEVEL="${AUTOMATION_LOG_LEVEL:-${LOG_LEVEL}}"

# :413 and :419 — both uvicorn invocations
--log-level "$(uvicorn_log_level "${LOG_LEVEL}")"

The two sides accept different vocabularies

Narrowing the value is not cosmetic. The application reads LOG_LEVEL through Python's logging module, which also understands the aliases WARN and FATAL, numeric levels, and NOTSET. Uvicorn validates --log-level with a click.Choice over critical | error | warning | info | debug | trace and exits 2 on anything else — before the service ever binds. Forwarding the env value verbatim would therefore turn a documented override into a crash: 

$ LOG_LEVEL=WARN npm run dev        # before this fix
Invalid value for '--log-level': 'warn' is not one of 'critical', 'error', 'warning', …
The automation backend exited during startup

A single normalizer — uvicornLogLevel() in JS, uvicorn_log_level() in the entrypoint — maps aliases to their equivalents (WARN → warning, FATAL → critical), numeric levels to the nearest name, and everything with no Uvicorn equivalent (NOTSET, 0, an unrecognized string) to info, which is what Uvicorn defaulted to before this PR set the flag at all. The environment value keeps its raw form, so the application still sees exactly what the user asked for; only the CLI argument is narrowed.

A latent bug fixed along the way

scripts/dev-static.mjs carries its own copies of both starters and was silently dropping --verbose: it parsed the flag into config.verbose but never passed it on, so verbose launches from that path were not verbose. It now threads the flag through to both services.

05Compatibility and risk

  • Standalone deployments are unaffected. The automation service keeps its INFO default; this PR only changes what Canvas passes when it spawns the service, plus the Docker image's fallback for an unset variable.
  • Not a breaking change for overrides. Anything already setting LOG_LEVEL keeps working, because the launcher defers to it.
  • Trade-off: a user who was relying on application INFO logs appearing by default now needs LOG_LEVEL=INFO. That is the intended change; the noisy default was the reported problem.
  • Not addressed here: selecting INFO still raises third-party loggers, because the pinned automation service silences sqlalchemy.engine but not sqlalchemy.orm in its own lifespan. Fixing that belongs in the automation repository and is tracked as a follow-up; see the PR notes.
